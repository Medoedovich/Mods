# Служебные события

Приоритет направления: **P0**. Статус: **Запланировано**. Категория: `system`.

[Все направления](README.md) · [Общий формат и правила](../LOGGING_SPEC.md)

Цель — понимать, когда и с какими настройками работал сборщик, были ли ошибки записи и насколько полны игровые данные.

## События и приоритет реализации

| Событие | Приоритет | Статус | Когда записываем |
|---|---|---|---|
| `system.logger_started` | P0 | Запланировано | После подготовки писателя и включённых категорий |
| `system.logger_stopped` | P0 | Запланировано | При штатной остановке, после сброса игровых записей и перед закрытием файла |
| `system.records_lost` | P0 | Запланировано | После обнаружения потерь, как только снова можно записывать |
| `system.health_sampled` | P0 | Запланировано | Раз в 60 секунд и при заключительной штатной сводке |

## Данные событий

| Событие | Данные сверх общего конверта |
|---|---|
| Запуск | Версии мода/игры, включённые категории, интервалы замеров, параметры очереди и ротации |
| Остановка | Причина, итоговые счётчики, сведения о незаписанном остатке, если он известен |
| Потери | Причина, число потерь по категориям, границы интервала, если известны; недоступные значения — `null`/`unknown` |
| Состояние | Размер очереди, число успешно записанных и потерянных событий, ошибки записи; интервал сводки |

У всех этих событий обычно `actor`, `target` и `position` равны `null`. Завершение процесса с аварией не обязано создавать событие остановки. Отсутствие остановки само по себе не доказывает потерю всех записей после последней сводки.

## Работы по этапам

| Работа | Приоритет | Критерий готовности |
|---|---|---|
| Конверт, UTC, ID запуска и последовательность | P0 | Записи различаются после перезапуска, каждая строка — валидный JSON |
| Ограниченная очередь и буферная запись | P0 | Ограничены память и работа на кадр; ошибки файла не останавливают игровой цикл |
| Ротация по дате UTC / 100 MiB | P0 | Продолжение записи после смены файла, уникальные имена частей |
| Учёт потерь и отказа писателя | P0 | Счётчики не теряют повторные отказы; после восстановления выходит сводка |
| Дополнительные замеры времени сериализации/записи | P1 | Можно оценить стоимость сборщика по наблюдаемым значениям |
| Сетевая доставка и подтверждение приёма | P2 | Повторная доставка сохраняет `event_id`; локальная запись остаётся доступной |

## Правила и проверки

- Счётчик `seq` назначается до постановки в очередь; пропуски помогают искать потери, но не заменяют их сводку.
- Если очередь заполнена, служебная сводка тоже может не попасть в файл. Держать счётчики вне очереди и повторить вывод после восстановления, без бесконечной рекурсии логгера.
- Проверить нормальный старт/стоп, аварийный обрыв, закрытый для записи файл, ротацию и переполнение очереди.
- При переполнении первым ограничивать периодические замеры и необязательные снимки; приоритет реализации P0 не определяет порядок отбрасывания.
- На старте могут быть незавершённая последняя строка и файлы предыдущего запуска. Инструменты должны отличать их от валидных событий нового запуска.

Зависимость: общий писатель нужен всем направлениям. Представление в инструментах — состояние сборщика, ошибки, потери, активные категории и периоды доступности данных.
