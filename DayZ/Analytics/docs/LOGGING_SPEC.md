# Спецификация логов Analytics

Версия проекта контракта: 0.1. Дата: 7 ноября 2026.

Это первая предлагаемая версия требований. Ни один пункт ниже не означает, что соответствующий перехват уже реализован или проверен в игре. Начальный фокус — поведение игроков и восстановление событий сессии.

## 1. На какие вопросы должны отвечать логи

- Когда игрок зашёл, сколько играл, вернулся ли после предыдущей сессии?
- Где он перемещался и где происходили значимые события?
- Какие вещи получил, передал, выбросил или потерял?
- Как добывал еду/воду, что употреблял и как лечился?
- Кто кому нанёс урон, каким средством и чем закончился бой?
- Где и при каких наблюдаемых обстоятельствах умер персонаж?

Первичный журнал хранит факты. Продолжительность сессии, маршруты, тепловые карты, активность по зонам, удержание и поведенческие сегменты вычисляются инструментами поверх журнала. Не записывать предположения вроде «читер», «рейдер» или «украл вещь» как установленные факты.

## 2. Приоритеты и категории

- **P0** — первая полезная версия: восстановление сессии, базовых действий и происшествий.
- **P1** — расширение контекста после проверки P0.
- **P2** — интеграции и дополнительная детализация по отдельной необходимости.

Коды категорий и событий на английском, подписи для интерфейсов — на русском. Одна запись имеет одну категорию. Событие смерти относится к `character`, хотя может отображаться и в фильтре боевых событий. Один факт не нужно дублировать ради разных разделов интерфейса.

| Категория | Название | Приоритет | Какие события планируются |
|---|---|---|---|
| `system` | Сборщик и качество данных | P0 | Запуск/штатная остановка сборщика, потерянные записи, контрольная сводка |
| `session` | Игровые сессии | P0 | Успешное подключение и отключение игрока |
| `character` | Жизнь персонажа | P0 | Создание или загрузка персонажа, смерть, изменение состояния сознания |
| `combat` | Бой | P0 | Попадания, агрегированные выстрелы; одиночные выстрелы только как опция P2 |
| `movement` | Перемещения | P0 | Периодические позиции; подтверждённые перемещения административными инструментами — P2 |
| `inventory` | Предметы и инвентарь | P0 | Подбор, выбрасывание и передача вещей одной записью перемещения; снимки инвентаря — P1 |
| `survival` | Питание и лечение | P0 | Еда, питьё, применение лечения; периодические показатели состояния — P1 |
| `crafting` | Крафт | P1 | Завершённое изготовление предметов |
| `building` | Строительство и разрушение | P1 | Установка объекта, постройка, разбор и разрушение части конструкции |
| `vehicle` | Транспорт | P1 | Посадка, выход, запуск/остановка двигателя, разрушение транспорта |
| `interaction` | Взаимодействия с миром | P1 | Открытие/закрытие объекта, закапывание/выкапывание тайника |
| `economy` | Торговля и счета | P2 | Покупка, продажа, изменение баланса через интеграции конкретных модов |
| `admin` | Действия администраторов | P2 | Выполненная админ-команда с оператором, целью и результатом |

Машиночитаемый перечень: [event-catalog.json](event-catalog.json). Параметр `planned_default_enabled` в нём обозначает предполагаемое включение в первом выпуске, а не текущую доступность события.

## 3. Минимальное содержимое событий P0

| Событие | Что сохранять дополнительно к общим полям |
|---|---|
| `system.logger_started` | Версия мода, версия игры, включённые категории, параметры интервалов |
| `system.logger_stopped` | Причина штатной остановки; при аварии такое событие не гарантируется |
| `system.records_lost` | Причина, число потерь по категориям, границы интервала, если известны |
| `system.health_sampled` | Размер очереди, число записанных/потерянных событий, ошибки записи |
| `session.player_connected` | ID новой сессии, имя, известный идентификатор аккаунта; факт успешного подключения |
| `session.player_disconnected` | ID сессии, последняя известная позиция с временем замера, причина выхода, если доступна |
| `character.spawned` | `spawn_kind`: `new`, `loaded` или `unknown`; ID жизни, если достоверно определён |
| `character.died` | Жертва, позиция смерти, наблюдаемый источник урона/убийца, средство урона, последние доступные показатели состояния |
| `character.consciousness_changed` | Предыдущее и новое состояние: `conscious` / `unconscious` |
| `combat.hit` | Источник и цель, их позиции, тип урона, оружие/боеприпас, зона попадания, дистанция, доступные значения здоровья до/после |
| `combat.shots_summary` | Игрок, тип оружия, число выстрелов, начало/конец окна агрегации; боеприпас, если доступен |
| `movement.position_sampled` | Позиция, причина замера, известное состояние движения/транспорта |
| `inventory.item_transferred` | Предмет, количество и единица измерения, места/владельцы до и после, позиции, причина переноса, если известна |
| `survival.item_consumed` | Еда/питьё, предмет или природный источник, фактически израсходованное количество с единицей, длительность |
| `survival.treatment_applied` | Кто лечил, кого, тип лечения, предмет, количество, наблюдаемый результат |

Особенности интерпретации:

- `combat.hit` включает наблюдаемый урон от игроков, заражённых, животных и среды; источник может отсутствовать. Физическое лицо, нанёсшее урон, записывается только при подтверждённой связи.
- Данные damage callback и фактическое уменьшение Health — разные значения. Если доступны оба, хранить отдельно `reported_damage` и `health_delta`. Не выдавать одно за другое.
- Причину смерти записывать как `unknown`, если она не подтверждена. Последний попавший игрок не обязательно является убийцей.
- В `inventory.item_transferred` явно различать `ground`, `hands`, `cargo`, `attachment`, указывать владельца/контейнер. Перекладывание между своими карманами по умолчанию пропускается. Подбор с земли, передача другому игроку, перенос в мировой контейнер и из него — сохраняются.
- При делении/объединении стака сохранять известный перенос количества, а не считать каждый callback новым полученным предметом. Если перенос не удалось сопоставить, качество события отмечается как `partial`.
- Для еды и лечения фиксировать фактический выполненный эффект. Итог одного действия агрегировать, а не писать запись на каждый внутренний тик. Если действие прервано после частичного расхода, сохранять расход и `outcome: partial`; простая отмена без эффекта в P0 не записывается.
- Начальную загрузку инвентаря при входе не считать подбором лута. Инвентарь на трупе не считать автоматически выброшенным игроком.

## 4. Общий контракт записи

Формат: UTF-8 NDJSON — один JSON-объект в строке. Все события используют один конверт; специфичные поля находятся в `data`.

| Поле | Требование и смысл |
|---|---|
| `schema_version` | Обязательно: целое число, первая версия `1` |
| `event_id` | Обязательно: уникальная строка, например `<server_id>:<server_boot_id>:<seq>`; повторная доставка сохраняет этот ID |
| `time_utc` | Обязательно: фактическое время события ISO 8601 UTC с `Z` |
| `server_id` | Обязательно: постоянный ID конкретного экземпляра сервера |
| `server_boot_id` | Обязательно: новый ID на каждый запуск сервера; отделяет перезапуски |
| `seq` | Обязательно: монотонный номер события в пределах запуска, назначаемый до постановки в очередь |
| `server_uptime_ms` | Обязательно: время с запуска сервера, миллисекунды |
| `map` | Обязательно: classname мира, например `chernarusplus` |
| `category` | Обязательно: код категории из каталога |
| `event` | Обязательно: полный код события, например `combat.hit` |
| `level` | Обязательно: `info`, `warn` или `error`; бой сам по себе не является ошибкой |
| `actor` | Обязательное поле: известный инициатор или `null`; игрок содержит `player_id`, `session_id`, `life_id`, `name` |
| `target` | Обязательное поле: игрок/сущность, над которой выполнено действие, или `null` |
| `position` | Обязательное поле: место события `[x, y, z]` в метрах либо `null`; для попадания — позиция цели |
| `data_quality` | Обязательно: `complete` или `partial`; оценка полноты обязательного контекста данного события |
| `data` | Обязательно: объект со специфичными данными события |
| `correlation_id` | Необязательно: связывает разные факты одного действия, например попадание и последующую смерть |
| `source` | Необязательно: точка перехвата/интеграция; подробности доступны в техническом режиме просмотра |

Правила идентификаторов и значений:

1. `player_id` — идентификатор аккаунта, а не имя. Для первой реализации выбрать DayZ GUID; доступный Steam64 хранить отдельным полем. Имена могут меняться.
2. `session_id` меняется при каждом новом успешном подключении. `life_id` обозначает одну жизнь персонажа и не должен меняться только из-за переподключения.
3. Пока нельзя надёжно восстановить `life_id` между подключениями, писать `null`. Не приравнивать его к `session_id` или результату `GetDatabaseID()` без проверки семантики.
4. `entity_runtime_id` относится только к текущему `server_boot_id`. `entity_persistent_id` заполнять лишь при подтверждённой стабильности ID между перезапусками.
5. При отсутствии игрока-инициатора использовать `actor: null`; источник среды/сущности описывать в `data`. В событии смерти жертва находится в `target`.
6. Неизвестное значение — `null` или согласованное перечисление `unknown`, а не `0`, пустое имя или координаты `[0, 0, 0]`. Отсутствие необязательного контекста само по себе не делает событие `partial`.
7. Количество всегда сопровождается единицей, например `count`, `ml` или `g`. Проценты/нормализованные показатели должны иметь явные имена или единицы. Не смешивать игровые условные единицы с физическими.
8. Порядок координат всегда X/Y/Z; Y — высота. Время DayZ хранить отдельным необязательным `world_time`, не заменяя UTC.
9. Версия документа `0.1` и `schema_version: 1` имеют разный смысл: версия требований и версия формата данных.

## 5. Частота и объём

Предлагаемые начальные настройки; подтвердить на тестовом сервере:

| Источник | Начальный режим |
|---|---|
| Подключения, смерть, сознание | Каждое подтверждённое событие |
| Попадания | Каждое подтверждённое попадание; не объединять разных источников/целей |
| Выстрелы | Сводка за 5 секунд по игроку и оружию; разные типы боеприпасов разделять, если доступны |
| Позиция | Проверка каждые 60 секунд; запись при смещении от последнего сохранённого замера минимум на 25 м |
| Стоящий игрок | Контрольный замер позиции не реже одного раза в 5 минут |
| Вход/выход, смерть | Дополнительная позиция в соответствующем событии; отдельную копию `position_sampled` не создавать |
| Перенос предмета, еда/питьё, лечение | Итоговое изменение, с подавлением повторных callback одного факта |
| `system.health_sampled` | Один раз в 60 секунд |
| Снимок инвентаря P1 | При подключении/смерти и по запросу; без постоянного полного обхода |

Точки позиции позволяют строить приблизительный маршрут. Они не показывают точную траекторию между замерами; разрыв, выход из игры и телепортацию нельзя рисовать как достоверный пройденный путь. Возврат в исходную точку между проверками может остаться незамеченным.

Запись должна идти через ограниченную очередь и буфер, с ограничением работы на кадр. Данные события копируются в момент факта: последующая сериализация не должна считывать уже изменившийся объект.

При переполнении сначала отбрасываются периодические позиции и необязательные снимки. Смерти, подключения и другие факты имеют более высокий приоритет, но абсолютная гарантия сохранения при аварии не заявляется. После восстановления записи выводится `system.records_lost` с точным известным числом потерь; если его восстановить нельзя, указывается `unknown`. Ошибка логирования не должна останавливать игровой цикл.

Начальная ротация — по дате UTC или достижении 100 MiB. Имя: `analytics_<server_id>_<server_boot_id>_<date>_<part>.ndjson`. Политика хранения задаётся отдельно после замера суточного объёма. Сетевую отправку и повторную доставку добавлять после стабильной записи локальных файлов.

## 6. Что показывать в инструментах

Основные фильтры: время, сервер/запуск, карта, категория/событие, игрок, сессия/жизнь, цель, тип предмета/оружия, область карты, полнота данных.

Первые представления:

1. Хронология игрока с подключениями, вещами, выживанием и боем.
2. Карта позиций и событий с разрывами между сессиями.
3. Карточка смерти с доступным контекстом и явными неизвестными значениями.
4. История получения/передачи/потери вещей.
5. Обзор категорий: число событий, активные игроки, ошибки и потери сборщика.

Русская подпись события берётся из каталога по стабильному коду. Фильтр «Бой» может включать `combat.*` и `character.died`, если доступный контекст смерти связан с боем. Такой фильтр не меняет категорию исходной записи. Инструмент удаления дублей использует `event_id`, а не текст сообщения.

Текст чата, содержимое голосовой связи, нажатия клавиш и данные сторонних сервисов в текущий набор требований не включены. Любое новое направление сбора оформляется как отдельная задача с конкретным вопросом для аналитики.

## 7. Порядок реализации и проверки

1. Проверить серверные точки перехвата, реальные единицы измерения и момент фиксации результата. Для каждого события пометить, какие поля доступны надёжно.
2. Реализовать общий конверт, NDJSON-писатель, ротацию и категорию `system`.
3. Добавить `session` и `character`; проверить вход, переподключение, смерть, новый персонаж, штатный рестарт и обрыв соединения.
4. Добавить `combat` и `movement`; проверить игрока, заражённого, падение, транспорт и разрывы маршрута.
5. Добавить `inventory` и `survival`; проверить стартовую загрузку, подбор/выброс, контейнер, передачу, стаки, частично выполненное питание/лечение и труп.
6. Замерить скорость генерации, размер файлов, очередь и время работы сборщика на кадр. Настроить интервалы по фактическим измерениям.
7. Добавлять категории P1 и интеграции P2 независимо; каждую можно включить/отключить в будущей конфигурации. Служебные сведения о потерях должны оставаться доступными.

Готовность P0: валидный JSON каждой строки; стабильные коды; различимые запуски/сессии/жизни; отсутствие подтверждённых дублей; корректные неизвестные значения; явный учёт обнаруженных потерь; проверенное поведение при заполнении очереди и ошибке файла; замеренное влияние на сервер. Численные пределы нагрузки согласовать после первого замера, а не обещать заранее.
