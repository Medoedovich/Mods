# Алгоритм отбора и экспорта данных мира

Пользователь утвердил этот порядок **05.10.2026**. Он задаёт правила реализации. Для баз-источников уже работает отдельный целевой экспорт и частичный снимок schemaVersion 2 с `Supplies/Harbors.json` в ревизии `r0002`. Широкая диагностика сохранена отдельно. Остальные разделы алгоритма ещё предстоит реализовать; запуск первого — в [SUPPLY_SOURCES.md](SUPPLY_SOURCES.md).

## Что читать и что сохранять

Начинать с выбранного сценария `.ent` и читать его загруженные слои, родительские миры, prefab и необходимые конфиги. Родительский Eden нельзя исключать целиком: он может содержать нужные объекты и именованные локации. Объём чтения для разрешения зависимостей может быть больше объёма сохраняемого отчёта.

В обычном экспорте сохранять только объекты выбранных разделов, необходимые связи и явно перечисленные поля. Не выгружать все поля компонента или сущность только потому, что её класс начинается с `SCR_Campaign`, `SCR_Ambient` либо `SCR_Resource`. Звуки, насекомые, декор и строительные настройки не входят в текущий объём отчёта. Связанный объект можно прочитать для получения нужного значения, не сохраняя его отдельной записью.

Для каждого раздела в коде должны быть явные правила: какие сущности / компоненты являются кандидатами, как подтверждается их категория, какие поля нужны, откуда они получены и в какой файл направляются. Добавление поля требует назначения в отчёте или для проверки / сравнения его данных.

## Последовательность

1. Записать метаданные выбранного сценария: версию игры / Workbench, режим чтения, дату UTC, путь и доступный GUID мира, зависимости и версию схемы.
2. Обойти источники сценария и зависимостей с защитой от циклов и повторного посещения. Для subscene сохранять путь исходного мира, когда он разрешён; один числовой индекс не объясняет происхождение объекта. Не зашивать правило «subscene 0 исключить» или «subscene 1 всегда Conflict».
3. Отобрать кандидатов по явным правилам разделов. Подтвердить тип и связи до включения в итог: наличие `SCR_ResourceComponent` само по себе не означает склад припасов, а affiliation сама по себе не означает группу ИИ.
4. Прочитать только нужные поля кандидатов и конфиги, необходимые для их разрешения. Учитывать наследование и override. Общий сбор всех доступных примитивных полей относится к диагностике.
5. Получить мировую позицию и нормализовать значения с единицами. Сохранять исходное значение при пересчёте: для source base `m_iSuppliesArrivalInterval` остаётся в секундах, минуты вычисляются делением на 60. `m_iRegularSuppliesIncomeBase` — пополнение за цикл; вместимость исследуется отдельно.
6. Сохранить записи сразу в набор своего раздела. Один обход может наполнять несколько наборов; промежуточный полный дамп сущностей не является обязательным шагом обычного экспорта.
7. Для нужных точек определить связанную / ближайшую именованную локацию по правилам TODO. Поиск может читать полный набор кандидатов, но в отчёт сохраняются используемые локации и необходимые сведения о неоднозначности. Source name хранится отдельно от игрового названия.
8. Проверить идентификаторы, отсутствие повторного счёта, полноту, числовые значения и ссылки. Записать JSON по разделам, затем построить каждую Markdown-таблицу из соответствующего сохранённого JSON.
9. После проверки перенести результат из `exports/` в новую ревизию архива и добавить ссылки в манифест. Существующие опубликованные снимки не переписывать.

Если объект нужен нескольким разделам, сохранять связи по ID; не суммировать его повторно. Несколько представлений одной базы допустимы, когда отчёты описывают разные свойства и явно связываются с одним источником.

## Разделы и необходимые данные

| Раздел | Что включать |
| --- | --- |
| ИИ | Точки появления и размещённые группы отдельно: ID, имя, мировая позиция, фракция, тип / prefab, состав и численность, случайные варианты, вероятность и условия появления |
| Припасы | Базы-источники, склады и тайники по отдельным категориям: ID, имя, позиция, связи с хранилищами, начальные припасы, вместимость, количество и интервал пополнения, подтверждённые условия дохода |
| Стартовые базы | Кандидаты HQ и правила выбора: ID, имя, позиция / направление, ограничения фракции, стартовые припасы, вместимость и настройки генерации |
| Машины | Ambient-точки, стартовые машины и выдача техники отдельно: ID, позиция / направление, категория, допустимые prefab, фракция, вероятность, лимиты и появление / повторный спавн |
| Именованные локации | Локации, используемые для описания выбранных точек: ID, ключ локализации, название и язык, позиция / область, источник; у точки — ссылка, способ определения и расстояние при выборе по близости |

Это перечень требований, а не заявление, что все поля уже найдены. Для каждой категории нужно сверить реальные классы и поля установленной версии игры. Неизвестное обязательное значение обозначать `unknown` и предупреждением; не заменять нулём и не удалять нужную запись молча.

У записи должны остаться сведения для проверки: ID источника, исходный мир / subscene и слой, prefab / config, компонент и поле, единицы, способ получения и признак override. Точный ресурс наследования нельзя подменять ближайшим prefab. Локальные координаты, второй расчёт позиции, подробная трассировка матриц и служебные поля сохраняются в диагностике; обычному отчёту нужны мировая позиция и необходимое происхождение результата.

## Файлы обычного экспорта

Иерархия остаётся прежней: `snapshots/<game-version>/worlds/<scenario-key>/`, для повторов — `revisions/<revision-id>/`. В следующем формате JSON каждого отчёта находится рядом с его Markdown:

```text
world.json
data.json                 # индекс разделов: пути, полнота и сводные метаданные
AI-Groups.json
AI-Groups.md
Supplies.md               # индекс таблиц припасов
Supplies/
  Harbors.json
  Harbors.md
  <other-report>.json
  <other-report>.md
Starting-Bases.json
Starting-Bases.md
Vehicle-Spawns.json
Vehicle-Spawns.md
Locations.json            # общий набор используемых именованных локаций
```

Для source base этот формат уже реализован в `r0002`: `world.json`, индекс `data.json`, `Supplies.md` и пара `Supplies/Harbors.json` / `Harbors.md`. Остальные пары и `Locations.json` показаны как план. Каждый JSON раздела — единственный источник записей своей таблицы; индекс не дублирует записи. `world.json` хранит общие метаданные, манифест версии — ссылки на ревизии. Общие локации будут связываться с точками по ID.

Несобранные разделы отмечать в индексе `not_analyzed`; не создавать для них пустые таблицы. Проверенная пустая выборка может иметь нулевой итог. Неполный раздел / снимок обозначать `partial`. Новый несовместимый формат получает следующую версию схемы; опубликованный `r0001` со schemaVersion 1 остаётся без изменений.

## Отдельная диагностика и проверки

Широкий JSON `HQC_Eden_Diagnostics_1.8.0.13.json` нужен для исследования и отладки. Его генерация должна быть отдельной явно выбранной командой / режимом. Обычный экспорт не должен требовать сохранения такого дампа. Диагностика остаётся в игнорируемом `exports/` и не является источником игровых итогов без нормализации.

При реализации проверить: полезный объект из родительского Eden включён; звук или насекомые исключены независимо от слоя; ресурсный компонент без подтверждённой связи с припасами не посчитан складом; повторная ссылка не создаёт дубль; неизвестные данные не дают ложный ноль. Сверить каждую таблицу с её JSON, повторяемость порядка и защиту опубликованных ревизий.

Текущий формат и переход: [DATA_LAYOUT.md](DATA_LAYOUT.md). Работающая диагностика: [SOURCE_DIAGNOSTICS.md](SOURCE_DIAGNOSTICS.md). Задачи реализации: [TODO.md](../TODO.md).

## Первый разбор вместимости: аэропорт

Целевой `ME_CA_StorageCapacityPlugin` раскрывает только `SCR_ResourceComponent.m_aContainers` выбранной source base и её потомков. Сохраняются иерархия, состояния ресурса, тип, вместимость и начальные припасы каждого слота. Физические контейнеры суммируются по уникальным ID; виртуальные представления сохраняются отдельно и не дают повторного счёта. Разный объём контейнеров внутри хранилища показывается отдельными записями и составом таблицы. `r0003` содержит только проверенную базу аэропорта; это не полный анализ вместимости всех баз или runtime-сети. Подробные правила — [STORAGE_CAPACITY.md](STORAGE_CAPACITY.md).

## Пакетный обход и неизвестная связь хранилищ

В r0004 алгоритм вместимости применён ко всем source base за один обход. Состав каждого хранилища остаётся в StorageCapacity.json; агрегат вместимости связан с записью базы в Harbors.json. Без физических потомков под базой показывать unknown, а не нулевую вместимость базы: отдельно расположенный склад может быть связан игровой ресурсной сетью. Близость сама по себе не подтверждает связь. Сохранять разные время / SHA-256 старого дохода и нового обхода вместимости. Перед обновлением корневой актуальной таблицы архивировать первоначальные данные r0001; канонические ревизии сохранять.

## Остальные физические контейнеры

Команда `ME_CA_WorldSupplyContainersPlugin` обходит все editor source в обеих subscene, читает только SCR_ResourceComponent и список m_aContainers с теми же четырьмя полями. В нативный JSON попадают SUPPLIES-слоты, виртуальные представления и неопределённые типы / списки с нужной родительской иерархией; разрешённые другие типы ресурсов и пустые компоненты отфильтровываются. Никакие runtime-сущности не создаются.

`New-OtherSupplyContainersReport.ps1` сопоставляет свежую инвентаризацию с каноническим отчётом вместимости предыдущей ревизии той же версии / сценария. Все ранее сохранённые физические и виртуальные слоты должны быть найдены и совпасть по ID, prefab, классу, значениям и координатам. Из физических исключаются уже известные контейнеры баз; оставшиеся сохраняются в OtherContainers.json. Виртуальные и неразрешённые записи идут отдельно, неизвестное не заменяется нулём. Каждый физический слот уникален; корневой source-предок используется для строки агрегата; ближайшее вложенное хранилище сохраняется отдельно. Это не назначение игровой базе.

Перед созданием каталога проверяются входы и все связи. После сохранения JSON из него строится Markdown с вместимостью, отдельным начальным количеством и мировыми координатами. Широкая диагностика не требуется. Команда и ограничения — [OTHER_CONTAINERS.md](OTHER_CONTAINERS.md).

В r0006 Markdown строится по корневым родителям: 124 строки для 568 физических контейнеров. Группировка по source ID корня сохраняет разные экземпляры одного prefab раздельно. Состав и суммы строятся по уникальным физическим слотам; unknown у дочернего слота делает итог родителя unknown. Позиции строк относятся к родителям. Детали остаются в JSON; прежнее время UTC и SHA-256 нативного входа не меняются.

## Именованные подписи и списки по радиусу

В r0007 ME_CA_LocationsPlugin читает только именованные MapDescriptor DisplayName / MainType / UnitType и проверенную мировую позицию, включая Eden. Сохраняет исходное имя, перевод и язык. New-LocationCatalogReport соединяет подписи с каноническими родителями OtherContainers и базами Harbors той же версии / сценария. Все пары с квадратом расстояния X/Z ≤ 1000² записываются как близость, не игровая принадлежность; проверка выполняется до округления. Неизвестные позиции / несопоставленные объекты остаются явно отмеченными; повторяющиеся имена разделяются по ID. Объекты хранятся один раз, в списках локаций — ссылки. Markdown строится из JSON. [Команда и алгоритм](LOCATION_CATALOG.md).
